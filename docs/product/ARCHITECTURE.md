# Anix Flow — архитектура v0.3

16 октября 2026. Проектная спецификация. Реализованный контур и целевой контур указаны отдельно.

## Цель и границы

Единая цепочка: задача клиента → бриф → общее ТЗ на драматургию и режиссуру → сценарии → правки/версии → подробная режиссура → экспликация → референсы → персонажи → изображения → видео → цвет → монтаж/звук → мастер.

Производство не является одним линейным статусом: можно согласовать одни сцены, дорабатывать другие, хранить несколько ветвей и получать производные от конкретных входных версий. Принятие результата означает принятие снимка с revision_id, а не постоянно меняющейся записи.

## Что существует сейчас

React + локальный FastAPI, Ollama/совместимый API, извлечение текста, паспорт задачи, Онтотон, акценты, ТЗ, сценарные варианты, проверки, localStorage, SQLite-копии, экспорт. Нет командной авторизации, общего Postgres, объектов медиа, надёжных фоновых jobs и монтажного renderer. Старые Mongo/Redis/Python-сервисы не считаются частью нового стабильного контура без отдельной миграции.

В этой итерации добавляются обзор маршрута проекта и версионные локальные копии с проверкой конфликтов. Это не замена командной платформы.

## Решение: модульный монолит и отдельные исполнители

| Компонент | Ответственность | Данные |
|---|---|---|
| Web UI | Рабочая область проекта, документы, редакторы, просмотр, таймлайн | Кэш и несохранённый черновик; сервер — источник общих данных |
| FastAPI/BFF | Авторизация, роли, команды предметной области, ревизии, audit | Postgres; optimistic concurrency |
| Domain modules | Brief/Spec, Script/Review, Direction, Assets, Media, Edit/Delivery | Явные контракты; не микросервисы ради разделения |
| Postgres | Транзакции, memberships, ревизии, зависимости, jobs/outbox | JSONB для расширяемых форм; связи и ключи — таблицами |
| Object storage | Документы, изображения, оригиналы видео, прокси, мастера | S3-compatible immutable object keys; не BLOB в Postgres |
| Queue + workers | LLM, OCR, генерации, transcode, FFmpeg/render | Celery + Redis как первая кандидатура, после измерения требований |
| Local agent | Доступ к Ollama и локальным файлам по разрешению | Отдельный локальный профиль; outbound polling при облачной работе |

Плюсы модульного монолита: меньше инфраструктуры, общие транзакции и проще отладка. Минус: границы модулей надо поддерживать явно; медиа-исполнители требуют отдельных ресурсов. Выделять сервисы после измеренного узкого места.

## Модель данных

Все серверные сущности принадлежат workspace_id; принадлежность и доступ проверяются на каждом запросе. Foreign keys не заменяют проверку роли. Для защиты от перепривязки чужих сущностей используются составные ключи/ограничения tenant + id и проверки в командах.

| Сущность | Основные ключи и инварианты |
|---|---|
| Workspace / User / Membership | Участник, роль; пользователь может состоять в нескольких рабочих пространствах |
| Project / ProjectMembership | Клиент, участники, настройки, текущие указатели ревизий; доступ клиента только к разрешённым материалам |
| DocumentVersion / SourceFragment | Оригинал, checksum, извлечённый текст, страница/диапазон, версия extractor; утверждение ссылается на фрагмент |
| BriefRevision / Requirement / Claim / Evidence | Неизменяемый снимок; provenance и explicit/inferred/unknown; подтверждение отделено от наличия цитаты |
| GeneralSpecRevision | Общая драматургия и режиссура; ссылки на brief_revision_id и версию словаря |
| Script / ScriptRevision / Scene / SceneRevision | Script — ветвь; Scene ID стабилен при перестановке; состав/порядок сцен хранит ScriptRevision |
| ReviewRequest / ReviewDecision / ChangeRequest | Объект, точная ревизия, роль/автор/время; комментарий к сцене/диапазону или timecode |
| DirectionRevision / Shot / ShotRevision | План внутри сцены; камера, композиция, свет, звук, длительность; shot_id не asset_id |
| ExplicationRevision / Reference / ReferenceUse | Что берём из референса и к какой версии решения это относится |
| Character / CharacterVersion / CharacterUse | Паспорт и ракурсы; проект закрепляет версию библиотеки |
| Asset / AssetVersion | Тип, object_key, sha256, mime, size, duration/fps/resolution, color metadata, происхождение |
| GenerationJob / JobAttempt / CostLedger | Модель, параметры, входные версии, provider_job_id, стоимость/лимит, попытки и ошибки |
| GradeRevision / DerivedAsset | Исходные версии клипов, цветовые пространства, параметры и LUT; оригинал не изменяется |
| TimelineRevision / Track / ClipInstance | Редакционное решение; asset_version_id, in/out, start, speed, track, transitions |
| RenderManifest / RenderJob / Delivery | Полный pinned manifest, профиль вывода, контроль, мастер и решение согласующего |
| Dependency / Invalidation / AuditEvent / Outbox | Точные связи по ревизиям, причины stale, события и надёжная отправка заданий |

### Сцена ≠ план ≠ клип ≠ монтажный фрагмент

Сцена — драматургическая единица. В ней несколько планов. План может иметь несколько сгенерированных видео-дублей. Один дубль может использоваться несколько раз и в разных монтажных версиях. Цветовая версия — производная от клипа/набора клипов. Монтажный фрагмент хранит in/out и позицию, а не копирует видеофайл.

Время монтажа хранится целыми кадрами/тиками с рациональным timebase (например, 24000/1001 fps), не накоплением float-секунд. Конверсия исходников с VFR фиксируется в metadata. Прокси и оригинал имеют явную связь; экспорт использует оригинал. Для звука отдельные дорожки, sample rate и gain/automation. Целевые loudness/peaks задаются профилем выдачи.

## Ревизии и согласования

1. Любая существенная правка создаёт immutable revision с parent_revision_id, автором и временем.
2. Изменение черновика проверяет expected_revision/ETag. Несовпадение → 409; сервер ничего не перезаписывает. UI предлагает сравнить и перенести изменения или создать копию.
3. Согласование указывает artifact_type + revision_id + actor + decision. Оно не переносится на новую ревизию.
4. Dependency pinning хранит конкретные входные версии. Изменение входа создаёт invalidation; старый результат остаётся доступным с предупреждением stale.
5. Не все downstream-объекты автоматически удаляются. Пользователь видит затронутые сцены/планы/рендеры и принимает решение о пересборке.
6. Сценарные циклы — ветвления графа ревизий, а не движение назад по общему project.status.

## API и фоновая работа

Команды: создать черновик, опубликовать ревизию, запросить просмотр, записать решение, создать генерацию, принять дубль, создать рендер. Общий PUT всего проекта оставляется для локальной копии и миграции, не заменяет предметные команды.

Mutation-команды используют expected_revision и Idempotency-Key. Команда и запись outbox сохраняются одной транзакцией. Dispatcher публикует job. Worker работает с pinned inputs, пишет попытки и терминальный результат; повторно доставленное сообщение не запускает платную генерацию второй раз. Для неясного статуса провайдера — unknown/reconciling, опрос provider_job_id и ручное решение; слепой повтор запрещён. Webhooks проверяются подписью и дедуплицируются.

Состояния: queued → running → succeeded / failed / cancelled; unknown для неясного внешнего исхода. Cancellation после отправки не обещает возврата средств. Retry ограничен классом ошибки, числом попыток и backoff. Результат сохраняется до подтверждения завершения. Для GPU/LLM/video/render отдельные очереди и лимиты конкуренции.

## Авторизация и работа с локальной LLM

Командный режим: OIDC Authorization Code; PKCE для публичного клиента/агента, серверная HttpOnly Secure SameSite-сессия для BFF, CSRF-защита мутаций. OAuth-токены не лежат в localStorage. Точный IdP выбирается при реализации по требованиям к размещению и доступности. Предлагаемые роли: owner, producer, editor, artist, reviewer, viewer. Доступ — deny-by-default. Клиентский reviewer не видит внутренние промпты, бюджеты и другие проекты без выдачи прав.

Локальный режим: один пользователь, loopback binding, Origin/Host allowlist, без ложной имитации многопользовательского входа. При подключении к облачному проекту агент получает ограниченный и отзывной доступ; делает исходящие соединения. Браузер облачного сайта не должен произвольно управлять localhost. Локальные ключи и учётные данные не экспортируются с проектом. Пользователь видит, какие документы и запросы уходят внешнему провайдеру.

Файлы: API проверяет membership и выдаёт короткий presigned URL для конкретного immutable key. Размер, mime, checksum и завершение загрузки проверяются перед принятием AssetVersion. Истечение ссылки не удаляет объект. Перезапись принятого key запрещается политикой приложения/хранилища.

## Надёжность и эксплуатация

- Postgres: миграции версионированы, expand/contract для несовместимых изменений, транзакции/ограничения и обработка конфликтов.
- Локальная SQLite: атомарные записи, revisions, busy_timeout, резервные снимки; экспорт для переноса. localStorage — рабочий черновик, не единственный архив.
- Общий контур: ежедневный backup + PITR при доступности платформы; object versioning/retention; шифрование транспортом и средствами выбранного хранилища.
- Целевые, ещё не измеренные RPO ≤ 24 ч и RTO ≤ 4 ч для пилота. Требования пересматриваются после оценки объёмов и стоимости. Восстановление проверяется в отдельной среде, не только наличием backup-файла.
- Logs: correlation_id/project_id/job_id; тела документов и секреты по умолчанию не логируются. Metrics: очередь, latency, ошибки, затраты, lost/unknown jobs. Проверки здоровья разделены на liveness/readiness и доступность внешних моделей.
- Acceptance before shared launch: тесты tenant isolation, конкурирующих сохранений, повторных jobs, восстановления БД/медиа, отмен и устаревших зависимостей.

## Этапы внедрения

1. Сохранность текущего local-first редактора и обзор проекта.
2. Версионные доменные контракты, general direction, сцены/планы и цикл правок.
3. Postgres + OIDC + роли + migrations, интеграционные тесты изоляции. До этого API остаётся локальным.
4. Object storage + outbox/queue + adapters; измерение стоимости и recovery внешних jobs.
5. Media preview, цвет, timeline и FFmpeg/render, только после закрепления сущностей и идентичности версий.
